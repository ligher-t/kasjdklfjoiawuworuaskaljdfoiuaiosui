# W03–W05｜事業所生成・生涯職歴・会計の実装前接続仕様

**2026-11-04／設計のみ。ゲームコード・イベント本文は未変更。**  
基礎：[雇用統合仕様v1.0](TERRA_19_REGION_EMPLOYMENT_INTEGRATED_SPEC_20261104.md)、[66組織](TERRA_EMPLOYER_AND_ORGANIZATION_REGISTRY_20261104.json)、[83職位条件](W02_POSITION_QUALIFICATION_MASTER_20261104.json)、[W01選択枝監査](W01_A175_CHOICE_SEMANTIC_TRIAGE_20261104.json)。現行コードを読み、実装時の所有者と操作境界を固定する。本文校閲の共通基準は[プロジェクト全般の文章／因果基準](../EVENT_PROSE_CAUSALITY_AND_REVIEW_STANDARD.md)。

## W03．仕事と勤務先の存在：世界側生成仕様

### 1．正本とID

| 概念 | 不変ID | 更新条件 |
|---|---|---|
| 生活圏 | `workAreaId` | 世界生成時に定義。主人公の住居訪問順・職業IDに依存しない |
| 産業の存在 | `workAreaId:sector` | 初期抽選／実在サイトの史料で確定。就職希望による再抽選禁止 |
| 組織 | `organizationKey` → `employerId` | 実在企業／家族の店／行政機関／共同体／秘密組織を区別。企業自体の同一性 |
| サイト | `siteId` | 実際の支店、製造施設、鉱区、研究室、宿、舞台、宮廷、作業集合場所。年月と地区を所有 |
| 職位 | `positionId` | サイトの担当業務、就業形態、資格、危険、給与基準。採用枠を持たなくても存在 |
| 募集 | `openingId` | 有効年月、受け入れ主体、定員、募集の公開度、応募窓口、審査結果と締切 |
| 非雇用生計 | `livelihoodOpportunityId` | 家業の役割、露店需要、農地や狩猟資源、単発請負、共同体活動など。法人や給与を要件としない |
| 事業所状況 | `siteOperationId` | 実年度・月の稼働、閉鎖、再開、災害、移転、需要変動、責任主体 |

**世界で共通するもの**を`s.world.occupationWorld`へ、**その人物が知った事実**を`workKnowledge[personId]`へ、**本人の具体的雇用**を`employmentRecords[personId][episodeId]`へ置く。学校P02の`educationAreaId`と街区・幹線を共用できるが、運営台帳は分離する。移動都市の地理IDは物理都市に紐づけ、到着／訪問順連番を雇用主IDへ使わない。

### 2．産業→企業／仕事口の生成

1. **固定史料**：`evidenceClass`, `sourceId`, `validFrom/validTo`, `regionId`, `cityId/areaId` のある実在サイトを先に確定。会社名があるだけ、商品の流通、知人が所属、輸出先という証拠では店や求人を作らない。ゲームで使用する日本語名は原文照合済みのものだけを正式表示。
2. **地域傾向**：19地域×13部門の既定表から`0/1/2/3`を引く。地区・資源・街道・工業集積・市街地の相関を共通の潜在値で与える。相関を無視した「鉱山・大学・病院・農園が一つの山村に乱立する」抽選を防ぐ。パラメータはゲーム仮定［S］。
3. **サイト類型**：会社本社・営業所・工場・研究所・官署・軍の駐屯・自営店・市場・組織拠点を分ける。例えば`rhine-lab`が一つあっても工場・主任研究室・サーミ調査所が全国全地区に現れることはない。
4. **供給と需要**：仕事の有無、職位、雇用主の欠員は別。主人公のためだけに一つの求人を空けない。地区の既知NPC数は総人口ではないため、**匿名の背景労働力**`latentWorkforce`と個別登場人物の実契約を区別し、実際にシミュレートしたNPCだけを背景母数へ二重計上しない。
5. **規模・採用枠**：各サイトに`capacityBand`（tiny/small/medium/large/unique）、稼働`staffSlots`、背景充足`latentOccupiedSlots`、個別人物契約枠、現年`openings`を持つ。値は［S］として設定する。関係式は`availableSlots=max(0,staffSlots−latentOccupiedSlots−activeNamedEmployees)`。規模・職務・年月から求人を生成するが、確率は`p_sector`と混同しない。募集のない現職は許す。
6. **特殊職と制度**：公証人役場、軍、審問官、企業騎士、ライン生命などの名称付き職は当該組織の`siteId`と`positionId`を参照し、資格・個別任命と募集枠を必要とする。氏族祭祀や家族の農作業は非公募`livelihoodOpportunityId`を使う。
7. **時間**：災害・戦闘・季節・廃業・再建の効果は`siteId`×`month`。新たな募集・サイト改修だけを年次更新し、既存の創業・採用・給与履歴を上書きしない。厳密年月が不明な史実は偽の日付を設定せず証拠の解像度を保存。
8. **決定論**：`keyedRoll(worldSeed,areaId,siteType,year)`型の独立・安定乱数。求人検索やUI描画で抽選しない。同じ土地を再訪した家族全員が同じ実在施設を共有する。

### 3．現行コードとの接続

- `js/world/facilities.js:facilitySpecsFor`は`s.job>0`から勤務先を追加する。**世界側サイト先行**へ移し、`activeFacility`の現窓口と`occupationWorld.sites`をIDで対応させる。既存ユーザーが暮らしていた合成施設は過去の接点の記録として残す仕様。
- `js/work/contracts.js:ensureWorkplaceLedger`は施設ごとに`staffSlots`・`openings`・`payScale`・`shift`等を確定し年次更新。新モデルではサイトの成立後にのみ適用し、`openings=0`は解雇でも廃業でもない。
- 人口の全シミュレーションを導入しない。背景労働力と表に現れるNPCを分ける簡素なモデルを採用し、想定外の自動雇用や上限超過を防ぐ。
- 働ける会社がない場合でも求人調査、紹介、訓練、転居、家業、非正規生計、見送りの進路が残る。

### 4．W03の受入条件

`siteId`がない職業だけを変更しても雇用主が増えない／空席がなくても現在の職は消えない／別NPCが応募しても過去採用の枠は勝手に再開しない／廃業後に再訪しても営業が復活しない／ロドスの診療先がそのまま採用先とならない／名前付き未照合会社は明示サイトに配置しない／サーミ等の非賃金活動が失業に集約されない。

## W04．生涯雇用・NPC／家族・職歴の有限状態機械

### 1．人物別の正本

`employmentEpisode`は`episodeId/personId/jobId/engagementKind/employerId/siteId/positionId/startedAt/status/endedAt/endingReason/contractId/parentEpisodeId/eventOutcomeRef/evidenceRef`を持つ。現在の`s.job`は**主たる仕事の表示用派生**。仕事の終了は過去の`episode`を閉じるだけで、技能・通った学校・過去の所得・友人関係を消さない。`lifeRecord.affiliations`は組織参加の別正本に参照を持ち、**療養相談**を雇用へ昇格させない。

| 前→後の状態 | 必要な確定証拠 | 同時更新 |
|---|---|---|
| 求職意向→求人発見 | 情報提供者・伝達経路・年月 | 本人の認知だけ、職歴と給与は不変 |
| 応募→選考 | 既知の募集ID・適格／書類・現地到達 | `workCaseId/applicationId`、必要費用のみ |
| 内定→承諾→勤務 | 採用決定、承諾、実勤務開始、契約者／現場 | `episodeId`・主職・勤務地・年次給与基礎を原子的に開始 |
| 家業・自営開始 | 本人意思、道具・農地／市場・住居・家族または共同体の実役割 | 雇用主なしの`episode`。在庫・収支または現物の正本 |
| 単発依頼受諾→実行→完了 | 依頼者、期間、仕事の実履行、支払条件 | `gigId`で対価一回。雇用主の常勤給与なし |
| 休止→復帰 | 病欠、旅、学業、介護等の理由と職場の継続、復帰の承認 | 就労月と給与の調整。主職・所属の停止と終了を区分 |
| 退職／解雇／徴用解除／廃業 | 実勤務先と契約・誰が終了させたか、原因と年月 | 職歴終了、必要な退職金・未払・失業・後続事案 |
| 同社異動／転勤 | 旧サイトと新サイト・新職位、移転や承認 | `episodeId`継承または新`episode`連鎖、前職歴は保持 |
| 死亡／強制隔離 | 当事者の死亡・拘束期間 | 実働・契約・家族への通知と負債を適正に清算 |

**多重の活動**：主職1件＋`secondaryEngagements`（1回請負、休業中の訓練、家庭・共同体の無給役割など）。仕事の重なりを許容する場合は就労時間・通学・生活の実在可能性を照合し、全職分の標準フルタイム年収を加算しない。学生の現職、在学中のアルバイト、老年の小商いを段階別に扱う。

### 2．家族の雇用を含む責任範囲

- `js/family/parent-household.js:advanceSeparatedParentHousehold`は親の`parent.j`と`workShare`から粗い賃金・家計を計算。新モデルでは親本人の`episodeId`があれば給与をそこから読む。実在するが詳細を知らない親の職場は、**背景の推定所得**として確度付きで扱う。父親が鉱夫だからという理由で鉱山を主人公の近所に必ず作らない。
- `js/family/adult-children.js:childHouseholdFinances`は成年子の`jobId`と`J.pay`から生活費への貢献を計算。成年子の転居時には職業が新たに選ばれる経路がある。各子本人の職場・勤務先・実居所から、所得と主人公が受け取る報告を**人別に**整理する。
- 親、配偶者、子、きょうだい、知人が同じサイトで働けば同一`siteId`を参照。別居家族が仕事を失っても、主人公の`jobId`や財布を変更しない。
- NPCの**真の職歴**と主人公の**認知履歴**を区別。家族から「仕事が見つかった」と便りが来た場合、その時点で知った範囲の仕事を表示。本人が知らない解雇・病状・勤め先は画面に出さない。

### 3．フラグと後続

`after`・`need`・`ban`・`eventOutcomes`を`episodeId/personId/contractId/selectedOutcome`に束ねる。`work_unemployed_reentry`は「現在求職している人物」の再度の案件。以前の求職失敗を後年の採用として再利用しない。単発請負が終わっていても、就業している主職と人生目標の完成をそれぞれ判定する。`s.fl.unemployed`等は現在の補助状態、`lifeRecord.careerChanges`は履歴。離職後の再採用は新しい`episodeId`である。

## W05．就業の賃金・現物・家計会計

### 1．現行計算の実コード観察

- `js/life/annual/personal-amounts.js`は`J[s.job].pay×region.pm×travelHomeWorkIncomeShare×contractIncomeFactor×personalWorkCapacity×(1+workPayBonus)×技能・知識・感染者への差別等の倍率`を中心に年間の収入を算出。**職業IDの所持と実際の就労期間の一致**が今後の改修点。
- `js/work/contracts.js:contractIncomeFactor`は呼出内で`reconcileWorkContract`を行う。新モデルでは収入の評価そのものによって契約新設／終了を起こさず、月末／年次確定フェーズで就労契約を確定した後、読み取り専用で会計を投影する。
- `js/life/annual/personal-cash.js`、`js/life/annual/household-budget.js`は本人・親・配偶者・子の収支が別正本。就労台帳が家庭の資金を無断で書き換えない。
- 同ファイルの`rhinePatentGrant`や職種による収入加算は、現行では職業条件から算出される部分を持つ。特許・発明の実績と支払主体・年度を記録し、職位保有だけで毎年同じ一時報酬を発生させない。

### 2．採用する支払単位

| 就労類型 | 発生条件と会計 |
|---|---|
| 賃金雇用 | `episodeId × payPeriod × wage`で予定給与と実働・欠勤・支給を分離。控除や天災休業は契約ごと |
| 公的任用・組織勤務 | 任命期間・給料・現物支給・軍の手当・支給遅延を別台帳 |
| 季節雇用 | その勤務季節だけ給与。来年も同じ募集があるかは独立 |
| 一件請負・単発護衛 | `gigId`と履行結果1回、前渡金・残金・破談・損害を分ける |
| 自営・家業 | 収入＝現金売上－仕入れ－経費－賃料－損失。本人給与と世帯共同売上の二重加算禁止 |
| 共同体・宗教的奉仕 | 受け取った住居・食料・燃料等の現物、共有家計、寄附・賃金がある場合だけ現金取引 |
| 強制配属 | 命令・拘束の労働記録。支払0、未払、現物等は現実の記録に従い、本人の同意済求人へ変換しない |
| 失職・休職・離脱 | 失職月以降の給与を止め、契約上の未払・治療・求職・年金・扶養は別に継続 |

会計の正本は`workEarnings[transactionId]`。最低項目：`personId,episodeId,employerId(or sourceId),payPeriod,accrued,paid,inKind,unpaid,basis,bookedAt,householdAccountId`。`transactionId=personId:episodeId:period:payType`等で冪等化。イベントの`cash/payBonus`・`workContractAction`と実支給は同じ支払根拠へ束ねる。前払金・臨時手当・退職金・賠償・賃金没収を通常年収の倍率に複製しない。

### 3．時間・旅行・家族への調整

`travelHomeWorkIncomeShare`で既に旅行中の不在を反映している場合は、その不在月を新しい`attendanceMonths`でさらに掛けない。どちらを正本にするかは実装時に一本化し、同じ不在月を一度だけ差し引く。勤務地に実際に赴いた日を年全体の常時勤務として扱わない。子の家計収入は本人の雇用主・給与と独立。未成年の職歴と家計奉仕は別扱い。病気・事故の因果が確認された場合、賃金だけでなく療養と負債への影響も各台帳に記録。

### 4．W03–W05受入例

| ID | 入力 | 必須の判定 |
|---|---|---|
| F01 | 職業J2になったばかり、稼働工場なし | `employerId`と月給は新規生成しない |
| F02 | 同じライン生命サイトに内部研究員1名と候補者2名、募集枠1 | 同時に2名採用しない。応募順・選考結果は固定 |
| F03 | 公共職位あり募集枠0 | 該当職員の給与は残るが応募不可 |
| F04 | 一回護衛任務が1か月で終了 | 報酬は履行時1回、翌年の通常年給なし |
| F05 | サーミの氏族に食料分配を担う親子 | 非現金の生計を保持し、架空企業を生成しない |
| F06 | 鉱区の監視付き強制労働と民間雇用 | 離職自由度・支給・未払を分ける |
| F07 | シエスタ旧施設の閉鎖→新移動都市へ移転 | 勤務終了・転籍・失業の実際の履歴を保持 |
| F08 | 主人公が3か月旅中、旧勤務先で雇用継続 | 不在控除は一度だけ。勤務地も家族住所も勝手に変更しない |
| F09 | 子の就職通知と別居 | 子本人の仕事・現実の居住先と主人公が知る所在地を分ける |
| F10 | 同じイベントをセーブ復元後再処理 | `episode`・採用枠・一時金・給与を増殖させない |
| F11 | 雇用主が発注を取り消すが給与が未払い | 支払済み扱いにせず債権と当事者を保持 |
| F12 | 同じ企業で見習いから正規職へ | 内部昇進の任命・昇給・責任変更を別実績へ |
| F13 | 友人から知る会社名と主人公の採用 | 社名を知るだけでは内定も勤務も成立しない |
| F14 | 仕事がない時期に自営の露店を準備 | 営業準備の費用と実際の売上の成立を別 |
| F15 | 会社が廃業後、戻った主人公が前職の同僚と再会 | 会社は再生成されず、面識と過去の職歴は消えない |

**引渡し**：本仕様は値の意味・不変条件・接続先まで定義。個別サイトの実在／募集期間の出典確度と、全A175イベントの選択ごとの最終文面承認はW01/W06で保持し、未承認の文章を勝手にイベントへ反映しない。
