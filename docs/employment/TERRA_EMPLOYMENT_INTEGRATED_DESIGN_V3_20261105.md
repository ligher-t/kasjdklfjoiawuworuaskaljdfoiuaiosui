## 2. 明示した採用・不採用政策

### 2.1 66組織を七つの経路に分ける

[EMPLOYER_PLAYER_ACCESS_POLICY_66_20261105.json](EMPLOYER_PLAYER_ACCESS_POLICY_66_20261105.json)の66件を一次キー `organizationKey` で固定する。以下は**ゲーム加入政策［P］**であり、原作上の全人事規則を述べるものではない。

| mode | 件数 | 主人公に認めること | 新規雇用 |
|---|---:|---|---|
| GENERAL | 17 | 実在サイト・職位・求人・選考が揃えば通常応募。名前付き企業も全国自動生成しない | 条件付き可 |
| SPECIAL | 32 | 特別任命、個別紹介、組織入隊、内部配属等の実証された経路 | 特別経路のみ可 |
| COMMUNITY | 3 | 氏族・共同体・家業での具体的役割や現物生計 | 通常求人不可、共同体役割可 |
| CONTACT | 5 | 依頼、社会関係、協力、利害衝突、紹介、短期請負 | 正式雇用不可 |
| BLOCKED | 2 | 非雇用の接触・委託・遭遇などは個別条件で可能 | **正式雇用・新規加入禁止** |
| HISTORICAL | 1 | 過去の組織活動・当時の関与記録。後年の新求人は禁止 | 現行時点の新規採用不可 |
| SOURCE_HOLD | 6 | 固有名や機関の日本語史料・制度が照合されるまで名前付き採用を保留 | 固有名採用不可 |

**BLOCKEDは `penguin-logistics`（ペンギン急便）と `lee-detective-agency`（リー探偵事務所）。** たとえ求人発見フラグ、会社サイト、職業ID、紹介者が存在しても、主人公を当該組織の正式従業員・所属者として新たに記録してはならない。配送業者J16・事務J21等の**汎用職からの横滑り配属も禁止**。この禁止はフィールドイベント・家族・自動初職・再就職・デバッグの通常生成経路にも通す。特別扱いで撤回する場合は本書・機械台帳の明示的改訂を要する。

CONTACTには無冑盟、マイレンダー基金、レム・ビリトン鉱業協会、龍門地下仲介網、シラクーザのファミリーを含む。これらについても「普通に就職して月給を得た」を作らず、個別事件・協力・任務・加入関係をその意味で記録する。特にJ64等の既存専用職は**新規採用発行経路を停止または意味別イベントへ移す**。過去セーブの実在する経歴を遡及削除しない。

HISTORICALのバベルは当時の存在と後年の会社設立を別に扱う。SOURCE_HOLDの現行ゲーム固有名称（サイバーニンジャ、東方重工、帝国科学院、司歳台/大理寺の統合職ラベル、金律法衛、ランデン修道院）は名前付き公募を凍結する。一般職や匿名の現実的な雇用先まで止めない。

### 2.2 採用を判断する実行順

すべての入口で、**最初に組織政策**を照合する。無許可な雇用を後から賃金計算で発見する構造を作らない。

```text
person + proposed position/employer
  → organizationKey, mode を決定（別名・子会社・職種IDを正規化）
  → BLOCKED/CONTACT/HISTORICAL/SOURCE_HOLD なら新規雇用を拒否
  → COMMUNITY なら communityRole の独立成立要件へ
  → GENERAL/SPECIAL なら、適用年代・場所・実稼働site・職位を検査
  → GENERALは求人・窓口、SPECIALは当該特別任命/紹介・採用権限を照合
  → 本人に伝わった情報、技能/資格、言語/身元/到達性、枠と審査
  → 実際の合否と本人の承諾、勤務開始日・勤務先を確定
  → 雇用episode・職業投影・履歴・会計を一原子的取引で開始
```

- 応募可能、応募済み、選考通過、内定、承諾、契約成立、勤務開始、賃金受取は別の意味。途中の段階で `s.job` や給与を確定しない。
- 正規の短期請負、秘密依頼、一回の配送・修理は `gigId` と依頼者・履行・実対価で処理。禁止組織と接触しただけで「所属」や「雇用」を付与しない。
- 企業の本社、支部、船の現在地、委託先、販売網は別。ロドス・ライン生命・BSW・カランド貿易等にも存在を根拠とした無条件募集を作らない。
- 原作未確認の国民共通免許、全国一律の感染者・種族排除、全時代一定の会社組織形態は創作しない。法律・個別就労規約を区別する。
- 雇用主への感染診断伝達と本人の感染状態は別記録。受け手の特定site/employerと有効年月・伝達経路が必要。

## 3. 世界・求職・就労・会計データの正本

**存在 → 情報 → 求職 → 採用 → 実勤務 → 支払 → 離職**の各段階を分離する。

| 正本 | キー | 必須責任 |
|---|---|---|
| `occupationWorld.areas` | stable `workAreaId` | 地域・都市・7地区類型・交通・地理・産業・年代。人物の訪問連番から導出しない |
| `organizations/employers` | `organizationKey/employerId` | 66台帳の分類、法的雇用主、年月付き所有/所属関係、確度 |
| `sites/positions` | `siteId/positionId` | 実稼働する拠点、職務、資格、規模、人数・配属・閉鎖/移転履歴 |
| `openings` | `openingId` | 採用主体、公開/非公開、開始/期限、欠員・募集権限・予約・選考 |
| `workKnowledge` | personId＋fact | 本人がいつ誰から何を知ったか。事実・噂・未確認を区別 |
| `workCases` | `caseId` | 意向、応募、審査、内定、受諾、失効の履歴。副作用なしの閲覧とは分離 |
| `employmentRecords` | `episodeId` | 主職、副職、委託、家業、任命、勤務期間、終了理由、過去所属 |
| `communityRoles/gigs` | `roleId/gigId` | 共同体内生計・単発依頼、現物や一回限りの報酬。法人雇用と混同しない |
| `workEarningsLedger` | `transactionId` | 賃金債権、支払、未払、現物、税・控除、原資、責任人物・世帯 |
| `employmentUx` | personId＋topicKey | 当人の求職方針、重要な選択の既提示、再催促抑制、継続案件 |
| `historicalTransitions` | siteId＋effectiveDate＋source | 災害・閉鎖・徴用・移転・再開の時間と地域スコープ |

現行 `s.job` は主たる実活動の表示投影であり、勤務先の実在を生成する権限を持たない。`s.workContract` や `lifeRecord.careerChanges`、`lifeAffiliations`、家族所得は各専門正本への互換投影にする。任意の表示・参照・給与見積は常にread-only。問い合わせ、ロード、同じ画面の再描画で時刻・世界seedのRNG・求人枠・事業所・契約・賃金を動かさない。

### 3.1 事業所生成と求人

1. `worldSeed + stablePlaceKey` で生活圏を先に固定。地区型・資源・交通等を決定。
2. 19×13の地域存在傾向を、地区/時代/歴史・地理補正と相関付き固定乱数で確定。名前付き会社の根拠サイトは先に明示。
3. 産業の存在から**あり得る一般の事業者類型**を生成。固有企業の部署・拠点を部門存在だけで複製しない。職位は現場の担当業務を持つ。
4. サイトごとに規模帯、定員、背景在籍人数、固有NPCの在籍人数、予約人数、募集予算・期限を持つ。`vacantSlots=max(0,capacity-aggregateOccupied-identifiedOccupied-reserved)`。予算や権限がないなら欠員があっても募集0。
5. 更新は年次/月次の確定フェーズでのみ行い、廃業・都市移転・歴史的災害の作用をサイトと年月に限定。同一seed再訪で求人が勝手に復活しない。
6. 家業・共同体・自営資源・季節請負は `livelihoodOpportunity` を別に持つ。すべての生計に会社や給与を要求しない。
7. SPEC上の採用頻度は実装後の較正対象。存在率4/20/55/85%を求人確率・就職成功確率へ流用しない。

### 3.2 初職と生涯FSM

- 初職は出生環境・学歴/資格・年齢・家族/縁故・地域労働需要・希望・本人に届く情報から**実際に開始できるepisode**として決定。未就業の人生を正当な結果とする。
- `workCase` の内部段階は `intent → discovered → verified → applied → screening → offered/rejected → accepted/declined → contracted → active`。休止/失職/任期満了/退職/死亡と再雇用は期間単位で保存。家業・自営・徴用には別の成立入口を持つ。
- 一件請負終了は仕事と支払いを閉じる。J4など常勤職への変換には別の実契約が必要。転勤は雇用主・支払主体・勤務地の区別。出向は二重所属があり得ても給与二重取りを防ぐ。
- 昇進は具体的職位の承諾・辞令・発効日に同期。単なる「内定」の文章でJ・給与を即変更しない。
- 雇用先と衝突する新規採用、過去終了済みsiteでの勤務、勤務可能時間を超える主職、副職、教育在籍・介護・拘束との衝突を検査。
- `s.job=0` は常勤職なしの投影。共同体役割、無給家事・家族商店補助、仕事探し、短期ギグを消さない。
- 家族・配偶者・親・成年子も同じepisode型を使えるが、背景の匿名労働者について全員の個別雇用生成は不要。NPCの事実と主人公が知る家族の近況を分ける。

### 3.3 収支と家族

- 月次契約の実労働分、短期ギグの実履行、自営は売上－費用、家業は共有収益と本人の対価、氏族・宗教的共同体は現物と現金を別記録。強制労働には無給・未払・拘束の意味を保存。
- 現在の `J.pay` は収入基準の参考値であり、就労の実体・月数を確認しない12か月一律給与へ変換しない。現金の予定・債権・実入金を区別。ライン生命の特許交付金は職名だけで毎年支給せず成果・決裁・支払で確定。
- `transactionId=personId:episodeId:period:payType` 等で冪等化。セーブ復元、同一イベントの再適用、勤務先の切替で二重受取しない。
- `travelHomeWorkIncomeShare` と勤務欠勤月の二重按分を解消する。年次モデルの既存死亡年収や家計処理の意味を独断で月次実収入へ書き換えず、出力の種類を明示。
- 親・配偶者・子の手取り、扶養、共有家計を別主体として扱い、別居者の職業変更で本人の勤務先・口座を動かさない。

## 4. UX規約：仕事の内部状態をすべて選択画面にしない

### 4.1 二層化

**内部**では、情報・募集・資格・選考・内定・契約・着任・労働・賃金を詳しく管理する。**画面上**では、人生を変える選択だけを提示する。

- `暮らしと仕事`：現職・勤務地・実勤務状態・未払、現在の求職方針・結果の概要、職歴を表示。
- `聞いた働き口`：**本人が知り得る**地域・職種・募集中の情報だけを一覧表示。会社名を知っても求人と断定しない。反復閲覧は副作用なし。
- `仕事を探す`：プレイヤーが希望条件（職域/現居住地重視/収入重視/危険回避/見送り等）を一度指定し、探索・書類確認・通常連絡は内部経過へ。毎回の「掲示板を確認する」「書類を出す」「返事を待つ」を独立した選択イベントにしない。
- `意思の確認`：最初の進路選択で「条件が一致すればこの仕事を引き受ける」か「採用条件を見てから決める」かを明示。**単に探すという選択をしただけで未承諾の正式雇用を成立させない**。既に許諾した上限内の条件なら採用結果を短い通知で確定し、重大な変更や危険な職務は改めて本人に選ばせる。
- `重要な分岐`：危険な職場、遠距離転勤、家族と別居、劣悪な条件、昇進、集団争議、強制配属、病気に伴う休職、解雇・失職への対応などに限り選択を要求。治療・感染・死亡・歴史事件の重要選択は仕事の都合で失効させない。
- `結果`：通常の不採用・情報収集・年次昇給の確認は短い非選択通知・人生記録・仕事画面へ集約。異なる企業の不採用結果を自動で連続する選択イベントに変換しない。

### 4.2 選択負荷の定量規約［P］

- **同じ通常求人案件のプレイヤー主要選択：基本1回、重要条件の追加同意が必要なら合計2回までを目標**。内部に10段階あっても10回の操作に変換しない。
- **自動発火する通常の就職関連選択が3回以上連続しない**ようにする。連続2回に達したら同類の次案件を保留・通知へ統合。加えて、**任意発火の主要選択5件の窓で通常就職関連は最大2件**を初期仕様とする。双方とも既存学校/医療/歴史/期限切れ重大選択の優先度より下位。自発的に仕事画面から開始した操作は連続抑制のカウント対象から除く。
- 連続判定は**実際にプレイヤーへ提示した選択イベント**で計算。非選択の日常ログや同じ画面の再表示ではカウントをリセットしない。明確な別テーマ選択、時間が経過して重要事実が変わった場合はルールに沿って新案件を提示。
- 必ず守る重要期限を、単に上限回数を満たすため黙って失効させない。期限が衝突した場合は一場面にまとめる、同一テーマの複数案件を単一の選択へまとめる、期日前の別枠を使う、本人の許諾に基づき内部で解決する。**選択不要な問題を生成して埋め草にしない。**
- 同じ求人・進路確認の再催促は、求人更新、資格/住所/家族状態の変更、明確な新情報等の `topicRevision` がなければ停止。無職・貧困だけを理由に毎月同じ求職選択を出さない。新情報がなければ本人が仕事画面から確認可能。
- `employmentUx[personId]` の `topicKey`, `topicRevision`, `decisionAsOf`, `lastPrompt`, `deferralUntil`, `consentScope` を期限付きで持ち、完了・辞退・失効による解除と再求職時の新 `caseId` を区別。単なる永続的な「就職したことがある」フラグで再転職を阻害しない。
- **重大な失職や徴用**などの強制イベントは任意の求人選択数に算入しない。ただし同一危機の多重表示・同じ相談の再選択は統合し、「5回連続の就職選択」を例外名目で発生させない。
- 有効な通常案件が0件なら、仕事画面には事情に応じた調査/家業/訓練/移動/見送りを残す。無理に採用の成功/失敗ダイアログを捏造しない。

### 4.3 既存イベントスケジューラとの接続

`js/events/dispatch.js:slot` は `majorEventMonth` による同月の主要選択制限、教育の未解決必須選択、期限付き医療、失効期限、旅の判断、現地歴史選択、予定後日談、優先選択という順序の保護がある。`js/events/eligibility.js:elig` は `once/cd/after.choice/outcome/excl` と同じ内容の再検討判定を持つ。**既存の保護優先順位を維持**する。

統合案：
1. 実イベントへカテゴリ `employmentDecisionKind = routine | material | critical | none`、`workTopicKey` を付与（名称・抽選値だけのregex分類禁止）。
2. `routine` を予定選択候補へ追加する直前に UX連続抑制・`topicRevision` と合致判定。採用案件の契約成立・金銭支払の適格性は別関数で必ず検査。
3. `material` は明示された追加同意が必要な場合のみ発火。`critical` は生命・拘束・期限・契約上の重大不利益に従って既存の期限保護へ接続。就職以外の必須選択に優先権を譲る。
4. 同じ `caseId` の通知、未払、求人更新、結果待ちは一つの提示単位へ集約。後続へ分ける必要がなければ結果文と履歴だけで確定。
5. 選択後に `eventOutcomes` と `workCase` の確定結果を記録し、待機や不採用の後日談は実際の結果へ結ぶ。旧 `sn` と `after` を無条件の採用成功扱いにしない。

**既存の教育/医療/歴史イベントの期限と職業イベントのUX上限が衝突したら、重要期限が優先する。** 結果を勝手に棄却しない。連続数のKPIはプレイヤーに選択を要求した実件数を数える。

### 4.4 表示ルール

求人情報は未発見/噂/確認済み/選考中/内定/契約/勤務中/終了を区別し、判定理由を一番重要な1〜2件に要約。不可理由は `unknown-to-person`, `no-site`, `site-closed`, `no-opening`, `route-unavailable`, `skill-gap`, `document-missing`, `certification-needed`, `waiting-result`, `offer-expired`, `unable-to-start` 等のW09辞書を参照する。

`BLOCKED` は**求人カード自体を出さず**、知人との出会い・物語上の接触は別の場面に残す。秘密活動の情報を「この組織はプレイヤー向けに就職禁止だから」と作中人物に説明させない。研究所への就職を阻む理由を本人が知らない場合も、内部の真相をUIへ漏らさない。

## 5. イベント・散文・後日談の統合改修

### 5.1 A175・703結果の適用順

[W01の結果裁定](W01_VERIFIED_SEMANTIC_FINDINGS_AND_REWRITES_20261104.md)の**P0 → P1 → P2**を採用。A175の静的な意味裁定は準備済みだが、全ての条件付き実行パス・動的ヘルパー・フラグ解除・後続のテスト合格を報告したものではない。実装時には結果単位で以下を同時に行う。

1. `sourceEventId, choiceIndex, outcomeIndex` の一意な原ソース・選択前提・採用や離職の意味を確認。
2. `organizationKey` のv3ポリシー、`siteId/positionId`、資格・権限、到達可能性、本人の知識を確認。
3. 結果文が成立を述べる場合は `workCase → episode` と `eventOutcomes` の**実結果**を同じ取引にする。不採用/辞退/中断では職歴・給料を増やさない。
4. 一時の護衛、徴用、家業・徒弟、大学進学、正式入社、昇進内定、勤務開始、退職/休職を別意味へ振り分ける。
5. 現職のみが条件の後日談は `episodeId/currentEmployerId` と当時の場所を照合。元雇用主との個人的な知己・告発・未払等は離職後も保持。
6. 全文・フラグ・認知・歴史と所属の接続を校閲し、**プレイヤーが見える改稿全文**は `docs/PLAYER_TEXT_REVIEW.md`へ登録。原文の散文を必要なく事務文へ置換しない。

優先例：`car` の放浪＝J1直接付与、`work_unemployed_reentry` の雇用先不在採用、`fam_inherit` の徒弟と家業承継、`fam_unemploy` の未成年就労、`choice_ursus_04` の兵站工場勤務、`choice_victoria_01` の工場争議、`choice_columbia_03` の研究所記録・解体、BSW昇進内定/減俸、`sr_rhine_rhodes_asylum` の薬局・ロドス分岐、感染者差別と企業通知。強制配属を自由応募へ変換しない。

B/C/Dの862候補は「職場がある」「その同僚と働いている」「前の会社が営業中」といった前提を持つものを優先。W12のB81復元資料で原文が回収されていても、実行時関数の効果と本人認知を確認してから承認する。既存36コンセプトとW11草案10件は**重複度を見て個別採否**し、46個まとめて追加という数合わせをしない。

### 5.3 共通の文章基準

本文は生活の細部から始め、目撃・伝聞・噂・本人が知らない企業情報を混同しない。選択肢は行為の相手と意図が判別でき、結果は成功・失敗・保留の実作用だけを描く。雇用の世界設計をイベントの地の文で長く講義しない。`J36`・`flag`・`eventId`・ゲーム上の確率や内部設計根拠を物語本文に出さない。原作日本語名称は日本語原典照合済みと未照合を区別。変更文章全文に加えて、フラグ・接続・校閲根拠を記録する。

## 6. 歴史・教育・地域・他システム接続

- **教育**：実際の `educationWorld.offering`、在籍・修了・学位・実技・言語能力を適用。専門医の臨床資格と研究者の学位を別にする。全地域に一律大学・医療学校があるとはしない。
- **歴史**：出来事の発生、都市の直接被害、地域への間接経済作用、本人の認知を別台帳で保持。1096チェルノボーグ、1098ロンディニウム、シエスタの旧市街/移動都市などの時空スコープを飛躍させない。
- **感染・差別**：疾病状態・診断通知・雇用主の認知・個別措置を別に記録。未通知の会社へ診断を自動伝搬しない。差別の実害は、事実として確認した場合には避けず描く。
- **移動**：勤務場所、実居所、家族/子の在籍先は独立。旅行中の契約維持、出向、通勤負担、閉鎖時の失職、移転の再採用と本人の知識を別々に更新。
- **NPC**：同一siteの定員を背景労働者と名有り人物で二重計上せず、親子の職歴と別居後の生活費を一つの会社状態で整合させる。
- **死亡年**：既存年次モデルの年収見積と実支給額を誤って同列にしない。亡くなった後に給与・再採用を開始しない。
